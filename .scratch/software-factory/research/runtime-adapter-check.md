# Runtime adapter and authentication check

Snapshot: 2026-10-03. Evidence for **Choose runtime adapters and authentication**, not a provider or product decision. Read official documentation and local version/help output only. No inference calls, credential inspection, authentication changes, SDK installation, or recovery tests were performed.

## Integration options

- **Codex app-server:** Official guidance positions this as the rich-client interface for authentication, history, approvals and streamed events. It exposes thread resume and turn start/steer/interrupt. Schemas can be generated from the selected binary so bindings match its version. Use the stable surface by leaving experimental capabilities disabled. Stdio is the default transport. This is the strongest documented candidate for AsmAI's browser-mediated conversation and approvals; that fit is our inference, not a validated implementation. [Official app-server documentation](https://learn.chatgpt.com/docs/app-server)
- **Codex SDK:** The documentation recommends SDKs for automated jobs and CI; TypeScript can start, continue and resume threads. Python controls local app-server and published builds include a pinned CLI runtime. SDK use is a viable alternative, especially if it exposes every interaction AsmAI needs in the eventual implementation language. Do not assume TypeScript and Python have identical underlying mechanisms. [Official SDK documentation](https://learn.chatgpt.com/docs/codex-sdk)
- **Claude Agent SDK:** Embeds Claude Code's tools, sessions, permissions, hooks, skills and subagents. The permission callback can obtain a human answer through the embedding application's interface. This is a stronger candidate than parsing terminal text for AsmAI's interactive requirements. [Overview](https://code.claude.com/docs/en/agent-sdk/overview), [Approval and input handling](https://code.claude.com/docs/en/agent-sdk/user-input)
- **Claude CLI:** Noninteractive JSON and stream-JSON include structured result/session metadata and support session resume. This is viable for bounded automated work. Bare mode excludes subscription credentials; standard CLI mode has different configuration/auth behavior. SIGTERM during an approval can leave it unanswered, so process exit alone is insufficient factory completion evidence. [Programmatic CLI](https://code.claude.com/docs/en/headless)

Session resume is not recovery of filesystem state or a proof of exactly-once external effects. Claude explicitly separates session conversations from files; AsmAI needs its own assignment/result reconciliation regardless of adapter. [Claude sessions](https://code.claude.com/docs/en/agent-sdk/sessions)

## Authentication choices and limits

- Codex documents ChatGPT sign-in and API-key authentication. API usage is billed separately from included ChatGPT usage; official guidance recommends API keys for programmatic CLI workflows. Enterprise access tokens are a separate account-controlled option, not an assumed entitlement. [Authentication](https://learn.chatgpt.com/docs/auth)
- OpenAI also documents app-server integration using an app-owned OAuth token authorized for ChatGPT-plan use. The app supplies and renews its own token; a completed inference request, not the model catalog, verifies access. This is a distinct integration route whose registration/availability constraints must be checked before promising it. It is not permission to extract another client's stored credentials. [ChatGPT-plan app-server integration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)
- Anthropic's Agent SDK overview says third-party developers cannot offer claude.ai login or rate limits for their products without prior approval, directing developers to API-key authentication. Therefore an API-key Claude adapter has a documented product route; subscription-backed distribution is conditional. This source does not establish permission for every conceivable personal wrapper, and an installed subscription CLI does not settle product distribution rights. [Agent SDK authentication guidance](https://code.claude.com/docs/en/agent-sdk/overview)
- The user must decide whether usage-billed API access is acceptable and whether launch is strictly personal or must already support distribution. Do not silently switch billing sources on failure or exhaustion; this is a proposed product constraint requiring the human's choice.

## Viable choices to present

1. Both Codex and Claude at launch: app-server plus Agent SDK is a plausible richer-integration pair. It broadens configuration and independent review choices but doubles provider qualification and authentication cases.
2. Codex first: app-server is a plausible first adapter with Claude deferred; simpler validation, no mixed-provider launch.
3. Claude first: Agent SDK with API credentials is a plausible first adapter with Codex deferred; same scope tradeoff.

These are recommendations and tradeoffs, not resolved choices. A SDK-backed Codex adapter remains viable if required approvals/interrupt/session behavior is demonstrated. Pure CLI orchestration is also possible but needs explicit handling of interaction and failures; it must not collapse genuine human gates into unconditional tool permission.

Before release, verify structured success/failure/interruption, permission denial and human response, session resume, expired credentials, usage exhaustion, and reconciliation after interruption against each pinned combination. ## Follow-up: user-installed CLIs with their own existing subscription login

The user clarified that both providers are required, API billing is unacceptable, and each developer installs and signs into the provider CLI themselves. That changes which integration route is relevant. The SDK warning above must not be read as a blanket prohibition on wrapping an unmodified Claude Code process.

**Claude Code has an explicit documented distinction.** Its legal/compliance page permits running the unmodified binary in products under Commercial Terms and stated conditions: retain its authentication methods, do not intermediate/resell usage, and let each end user authenticate and be billed directly, including through their subscription. It separately prohibits collecting/intermediating Claude account credentials and product-owned Claude login. Thus there is a documented own-login binary route; it is different from supplying subscription tokens to a custom SDK product. The page also says advertised subscription limits assume ordinary individual use. [Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)

Subscription-only support in AsmAI should therefore mean AsmAI requires that mode and refuses to dispatch on a different billing source; it should not alter or disable the underlying binary's authentication choices. Whether that precise enforcement constitutes a restriction under the published condition is not conclusively defined in the source. Avoid claiming unconditional permission for arbitrary orchestration intensity, resale, or commercial arrangements.

**Codex distinguishes managed login from external tokens.** Managed `chatgpt` authentication leaves token persistence and refresh with Codex. The app-server documentation explicitly allows continued use for local or open-source applications, recommends migration to Sign in with ChatGPT, and excludes commercial or hosted services from app-server authentication. An externally owned token lifecycle is a separate experimental mode and is unnecessary for the requested existing-login route. [Codex app-server authentication](https://learn.chatgpt.com/docs/app-server)

An open-source application run by each developer on their own machine is the clearest documented Codex category. The source does not precisely classify a developer's private remote execution host versus a hosted service, nor establish that every paid self-hosted distribution qualifies. If commercial/managed-hosted distribution is required, that classification needs explicit provider confirmation or a different supported auth route. This is a product-permission boundary, not a discovered technical failure.

**Technical capability remains separate from permission.** Claude documents subscription login in its ordinary binary, noninteractive execution, and an explicit bare-mode exclusion of subscription login. Together they support investigating ordinary `claude -p` under the already-signed-in user's environment. [Claude authentication](https://code.claude.com/docs/en/authentication), [Programmatic CLI](https://code.claude.com/docs/en/headless) No run has verified credential selection, subscription billing, interactive approval bridging, concurrent workers, or recovery in either provider. The user's proposed route needs those tests; no evidence requires AsmAI to read or copy credential files.

## Follow-up: common CLI orchestration first

The user chose to investigate a common CLI approach before selecting a Codex app-server / Claude CLI pair. A common semantic contract is plausible; identical flags or interaction channels are not established.

**Verified interfaces.** Codex offers `exec --json`, final output schemas, and `exec resume <SESSION_ID> <PROMPT>`. Its documented use is a noninteractive run with preselected permissions. Local `0.157.0` help exposes sandbox selection, automatic approval review, bypass flags and config overrides, but no interactive permission-response channel or streaming input protocol. We did not establish its precise fallback for every approval configuration; do not claim a live permission callback exists. [Noninteractive guide](https://learn.chatgpt.com/docs/non-interactive-mode), [Command reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli)

Local Claude `2.1.283` help exposes print mode, JSON streaming input/output and explicit session resume. Its documentation also describes an MCP permission host selected with `--permission-prompt-tool`: a hosted request waits for an answer; ordinary print mode without a host denies unresolved permission requests. That is a provider-specific mechanism requiring qualification, not a capability shared with Codex exec. [Claude programmatic execution](https://code.claude.com/docs/en/headless)

**Two different gates must remain distinct.** A planning/skill question can be an application-level result: the agent emits a question and stops its turn; AsmAI records waiting state; the actual human answers; AsmAI resumes the explicit session with that answer. This is a proposed design supported by both CLIs' continuation surfaces, not a tested guarantee of obedience. A provider-native tool permission request is different: outputting “approved” in the next prompt does not itself grant that tool permission or answer a pending provider request.

Proposed shared adapter semantics: start an explicitly scoped turn; stream normalized progress; capture provider/session/attempt identifiers; return a typed outcome (result, human question, blocked permission, authentication failure, limit exhaustion, failure, interruption, unknown); resume a known session after a genuine answer; request stop and reconcile actual effects. Provider-specific flags/events remain behind each adapter. A finished turn is not accepted assignment completion. Use explicit IDs rather than either provider's most-recent-session shortcut under concurrency.

**Recommended decision:** adopt CLI-first as a candidate to qualify, with a focused prototype ticket before certifying it as the final adapter design. Test both providers returning a structured human question with no dependent action, a real answer round-trip, denied tool permission without bypass, cancellation during a tool, missing terminal events, session identity isolation, and restart/resume. Verify an allowed next step after human approval without broadening unrelated permissions. If the Codex tool-permission path cannot satisfy the chosen requirements, return that concrete gap to the user for a choice of app-server or a narrower execution contract. Do not silently substitute transports or automatic approvals.

The common approach neither initiates login nor copies credentials: developers prepare provider authentication outside AsmAI; an unusable session produces a blocked outcome. No model calls or permission experiments were run in this research.

## Follow-up: direct interactive terminals

Moving the human conversation into each provider's ordinary interactive terminal removes the need for AsmAI to reproduce native prompts in a browser. This is a feasibility inference, not a chosen scope change. Claude documents background sessions and terminal attachment; local `2.1.283` help exposes `--bg` and `attach`. Codex exposes interactive CLI/resume and a remote TUI backed by app-server. A session manager can preserve access to an interactive process, but attaching does not turn a noninteractive print/exec run into a different supported protocol. [Claude CLI reference](https://code.claude.com/docs/en/cli-reference), [Codex command reference](https://learn.chatgpt.com/docs/developer-commands)

Interactive operation need not require scraping all orchestration state from terminal pixels. Codex documents hooks including session start, prompt submission, permission requests, Stop and Interrupt, with session/turn identifiers. Its transcript format is explicitly not a stable hook interface. Claude documents Stop and failure hooks; Stop means response ended and does not fire on user interruption. These are candidate structured integration signals that require pinned-version qualification, not complete durable delivery guarantees. [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Claude hooks](https://code.claude.com/docs/en/hooks)

Terminal access leaves AsmAI responsible for assignment identity, sole owner, result acceptance, handoffs, pending human decisions, side-effect reconciliation and restart recovery. A stopped turn or idle terminal is not proof that an assignment met its criteria. Direct interventions must also preserve the existing owner/handoff policy. A terminal-first prototype should test a real human approval, detach/reattach, blocked-worker notification and evidence-backed result acceptance before selecting a session manager. No runtime was launched or session manager selected.
