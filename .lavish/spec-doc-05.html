Q1

A repository that asks for rebase, when pushes are never forced

Go to “Keeping current and conflicts” in the document

The sources conflict. AssemblyAI#11 says the job branch merges the base in unless the repository instructions ask for a rebase, and that pushed history is rewritten only when the repository instructions require it, and then with force-with-lease. AssemblyAI#18 and ADR 0007, decided later, say the daemon pushes the job branch with a plain push that is never forced, and that repository instructions never decide how the branch is pushed.

The job branch is first pushed at delivery (AssemblyAI#18), so a rebase before then needs no force. A rebase after it, for example to take in a moved base during review or in a follow-up job, would.

Rule 22 in the draft is open until you answer.

Recommended: A. It keeps ADR 0007's "never forced" without an exception, still follows the repository's rebase convention for everything you have not seen yet, and says where it could not. B reopens the one push rule ADR 0007 made absolute, and a forced push on a PR under review rewrites the history you were reviewing. C ignores the convention even where following it costs nothing.

Q2

How are one-at-a-time checks declared and run?

Go to “Workspaces” in the document

Settled: a repository whose checks cannot run side by side says so, and agents run those checks through an `asmai` command that takes turns per repository (AssemblyAI#11); AssemblyAI#27 lists one-at-a-time checks among the per-repository settings. The sources do not say what the declaration holds or name the command.

Rule 11 in the draft leaves both open.

Recommended: A. The repository's checks (tests, lint, build) are what workers are already told to run, so one switch covers them without a list to keep in step with the repository. With B, a command missing from the list, or run with other arguments, runs side by side unnoticed. `asmai turn` says what it does; give another name in the notes if you prefer one.

Q3

How are job and assignment branches named?

Go to “The job branch” in the document

No ticket names them. The job branch becomes the pull request's head branch, and assignment branches stay on origin until you delete them (AssemblyAI#11), so their names show in the PR and in the repository's branch list. Repository instructions decide how work is done in a repository (AssemblyAI#11), and some set a branch-naming convention.

In both options the slug comes from the job's title, and a follow-up that continues an open PR keeps its job branch.

Recommended: A. The daemon can name the branch itself when it makes it, without an agent reading the instructions, and everything AsmAI made sits under `asmai/` for you to find and delete. B honours conventions on the branch reviewers see, at the cost of an agent supplying the name for each job.

05 Repositories and job branches

This document specifies how jobs work in repositories: the registry, AsmAI's own clone, workspaces and assignment branches, the job branch and its fast-forward on acceptance, keeping it current, conflicts and outside commits, notes, the leaders' view, repository instructions, commit trailers and cleanup. 06 Validation and delivery specifies how the finished job branch is validated, pushed and opened as a pull request.

Rules

The registry

  1. Registered repositories only. Jobs can target only repositories the user has registered. The user registers them with asmai repo add <path-or-url>; Coordination tells the user the command and never registers one itself (AssemblyAI#9).
  2. What registration records: a name, the repository's location on the host, its origin remote and its default branch (AssemblyAI#9).
  3. Listing and removing. asmai repo list|show|remove list, show and remove registered repositories. Removing a repository with open jobs is refused (AssemblyAI#9).
  4. Setup on registration. Registering a repository without docs/agents/issue-tracker.md makes Coordination open a setup job (AssemblyAI#17, 08).

AsmAI's clone

  1. Never the user's checkout. Each registered repository has an AsmAI-owned clone in the state directory, fetched from origin, and every workspace is made from it. The user's own checkout is never used, although the registry records where it is (AssemblyAI#11, ADR 0005).

Workspaces

  1. The daemon owns them. The daemon creates each workspace when it dispatches the assignment, starts the worker inside it, and is the only party that creates or removes workspaces (AssemblyAI#11).
  2. Writing and read-only. A writing assignment works on its own assignment branch, made from the job branch's tip. A read-only assignment's workspace is fixed at the commit it examines, and its evidence names that commit (AssemblyAI#11).
  3. No repository. In a job without a repository, each assignment gets an empty scratch workspace (AssemblyAI#11).
  4. Staying inside. Staying inside the workspace is part of every worker's instructions, and any write outside it is an effect to record. The providers' qualified write guards are switched on as a guard against mistakes, not as a security boundary (AssemblyAI#11, 03).
  5. Slots. Every workspace gets a slot number and its own temporary directory, given to the worker as ASMAI_SLOT and TMPDIR (AssemblyAI#11).
  6. Checks that cannot run side by side. A repository whose checks cannot run side by side says so, and agents run those checks through an asmai command that takes turns per repository (AssemblyAI#11). How it is declared and the command's name: question Q2.
  7. Disk. Below the free-space floor on the state directory's volume, the daemon creates no new workspace, and the assignments waiting for one hold (AssemblyAI#14, 07).

The job branch

  1. One per repository job. Each repository job has one job branch, which becomes its pull request. It starts from the default branch as fetched from origin, or from another origin branch the user names, and the job records the commit it started from (AssemblyAI#11).
  2. Branch names. Question Q3 decides how job and assignment branches are named.
  3. One writer per branch. Only one party writes a branch at any time (AssemblyAI#11). The daemon is the only party that ever moves the job branch, locally or on origin (AssemblyAI#18).
  4. One open job per job branch. A job branch belongs to one open job at a time. A follow-up to a job whose pull request is still open continues on that job branch and pull request, starting from origin's copy. Once the pull request is merged or closed, a follow-up starts from the base with a new job branch and pull request (AssemblyAI#11).

Accepted work

  1. Workers take in the tip. A worker takes in the job branch's tip before submitting a result (AssemblyAI#11).
  2. Fast-forward on acceptance. When the owning leader accepts a result with asmai accept, the daemon fast-forwards the job branch to the accepted commit as part of recording the acceptance (AssemblyAI#11, ADR 0005).
  3. A moved tip. If the job branch moved after the result was submitted, the work returns to the same worker to take in the new tip and submit again. This is not a rejection (AssemblyAI#11).
  4. Workers resolve conflicts. Conflicts are always resolved by a worker inside an assignment, never by a leader or the daemon (AssemblyAI#11, ADR 0005).

Keeping current and conflicts

  1. Taking in the base. The job branch takes in the latest base before it is offered for review and before each later push (AssemblyAI#11).
  2. Merge or rebase. Question Q1 decides how a repository whose instructions ask for a rebase is handled, because AssemblyAI#11 and AssemblyAI#18 conflict. Otherwise the base is merged in (AssemblyAI#11).
  3. Conflicts are ordinary work. Resolving a conflict is ordinary writing work, and a choice between distinct viable approaches in it goes to the user (AssemblyAI#11, 01).
  4. Concurrent jobs in one repository run with no locks and no overlap report. A conflict is resolved in whichever job meets it when its branch is brought up to date (AssemblyAI#11).
  5. Outside commits. Before every push, the job's branch is fetched from origin. Commits AsmAI did not make are kept and merged in by a worker, recorded as an outside change and reported in one line; they are never force-pushed over (AssemblyAI#11, AssemblyAI#18). After a restore, commits pushed since the backup count as outside changes (AssemblyAI#20).

Branches on origin

  1. Assignment branches are pushed. A worker commits and pushes its assignment branch whenever it submits a result, reports that it is blocked, or is cancelled, committing any uncommitted changes first. Each push is an effect (AssemblyAI#11).
  2. Part of every mandate. Pushing assignment branches and the job branch is part of every repository job's mandate, including research-only and planning-only jobs (AssemblyAI#11).
  3. Kept until the user deletes them. Assignment branches stay on origin until the user deletes them, and none is opened as a pull request (AssemblyAI#11).

Notes and prototypes

  1. Not copied from the tracker. A note that its workflow already records in the issue tracker, such as a resolution comment or a PR review, is not copied anywhere (AssemblyAI#11).
  2. Other notes go on the job branch. Any other note, such as research findings or a diagnosis log, is committed to the job branch by a writing assignment. It goes where the repository already keeps such notes, according to its repository instructions or existing folders, and otherwise under docs/<kind>/; the result says where (AssemblyAI#11).
  3. Prototypes stay on their branch. A prototype stays on its own assignment branch on origin. Its verdict, with a pointer to that branch, is a note (AssemblyAI#11).
  4. Notes deliver like code. A repository job whose outcome is notes is delivered like any other: its job branch is pushed and opened as a pull request holding its notes, for the user to review and merge (AssemblyAI#11, 06).

The leaders' view

  1. One read-only view per repository job. The daemon keeps one read-only view of each repository job at the job branch's tip, refreshed whenever the branch moves. Leaders read code and repository instructions there, and the job's brief points to it. Leaders never write in it, and it is not a workspace (AssemblyAI#11).

Repository instructions

  1. Instruction files apply. Agents follow the repository's instruction files, and both providers see AGENTS.md and CLAUDE.md, whichever exist. The user's notes for the repository in AsmAI's configuration count as repository instructions too (AssemblyAI#11).
  2. Provider configuration does not. The repository's provider configuration (.claude settings, hooks, permission rules, MCP servers and .codex configuration) is never loaded (AssemblyAI#11).
  3. Loading instruction files. Whether a provider loads instruction files without loading project configuration is qualified per provider version; AsmAI can always pass their content itself (AssemblyAI#11).
  4. Never wider than the mandate. Repository instructions decide how work is done in the repository but never widen a mandate. A conflict between them and the mandate is escalated (AssemblyAI#11). They never decide how the job branch is pushed (AssemblyAI#18, 06).

Commits

  1. The user's identity. Agents commit with the user's git identity and use the user's existing git and gh credentials. AsmAI handles no tokens (AssemblyAI#11).
  2. Trailers. Every commit carries AsmAI-Job, AsmAI-Agent and AsmAI-Dispatch trailers, which a repository whose conventions forbid trailers can switch off (AssemblyAI#11).

Local cleanup

  1. Writing workspaces are removed once their work is on the job branch, and read-only workspaces when their assignment ends (AssemblyAI#11).
  2. Kept for reconciliation. A workspace whose assignment needs reconciliation is kept until the reconciliation is recorded (AssemblyAI#11).
  3. Kept until the job ends. The workspace of cancelled or abandoned work is kept until the job ends; its work is already pushed (AssemblyAI#11).
  4. At the end of a job, everything local to it is removed, and its branches on origin stay (AssemblyAI#11).
  5. Scratch workspaces of a job without a repository are kept after the job ends, until the user removes them with asmai job clean <n>, which is refused while the job is open (AssemblyAI#11, AssemblyAI#14).
