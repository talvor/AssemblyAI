04 Conversation and Lavish

This document specifies the user's two ways of talking to the factory: the conversation with Coordination in its interactive terminal, and the Lavish pages where reviews and questions are answered. It covers the focused job, one-line updates, the catch-up, unsent text, a second attach, the Lavish server, rendering decision requests and collecting answers. 01 Roles and decisions specifies which decisions go to which surface and how answers are attributed; 03 Provider sessions and terminals specifies the attach client and its status line.

Rules

The conversation

  1. Coordination's terminal. The user's primary conversation is Coordination's interactive provider terminal (AssemblyAI#15). A bare asmai, or asmai chat, opens it, starting a stopped factory first and saying so (AssemblyAI#9).
  2. Not an intervention. The conversation is not an intervention: leaving it returns Coordination to automated delivery at once, and never pauses anything (AssemblyAI#9, AssemblyAI#10).
  3. Delivery never waits for the user. Coordination keeps delivering automated items while the user talks, and delivery never waits on whether the user is present (AssemblyAI#10).
  4. Never over the user's text. The daemon never types into the conversation while the user has unsent text in it (AssemblyAI#9). A nudge waits until the user submits or leaves (AssemblyAI#10).
  5. The user's keys always arrive. The user's keys always reach the conversation, including Esc during an automated turn (AssemblyAI#10).
  6. An interrupted automated turn is nudged again afterwards. Coordination re-reads the same messages, which reads by message ID make safe, and checks its own recorded asmai calls before acting again, so nothing is blindly repeated (AssemblyAI#10).

Updates and decisions in the conversation

  1. One line per item. Each automated item appears as one line tagged with its job number. Anything that needs the user appears as a flagged block. Detail is given when the user asks (AssemblyAI#10).
  2. Job numbers everywhere. Every Coordination line about a job carries the job's number (AssemblyAI#10).
  3. Escalated once. A decision is presented once, with its answer surface, and the status line keeps it visible until it is answered (AssemblyAI#10, 01).
  4. Answering here. A decision whose answer surface is the conversation is answered by the user's message in it. Coordination records the answer with its reading beside the user's witnessed message (AssemblyAI#10, 01).
  5. Acting on the user's word. When the user tells Coordination to pause, resume or cancel a job, it acts citing the user's witnessed message (AssemblyAI#14, 07).

The focused job

  1. One focused job. The conversation has one focused job. The user's messages apply to it unless they name another job (14: … or job 14) (AssemblyAI#10).
  2. Switching. "Switch to 14" moves the focus; Coordination says so and loads that job's brief (AssemblyAI#10, 02).
  3. New requests. A new request opens a job, which takes the focus. Factory-wide questions need no job (AssemblyAI#10).

Leaving and coming back

  1. What leaving is. The user leaves the conversation by detaching, by moving the terminal elsewhere with the Ctrl-] menu, when the terminal or SSH connection drops, or when a newer attach takes the conversation over (AssemblyAI#10, 03).
  2. Unsent text. Leaving saves the user's unsent text to the journal, clears Coordination's input box at the next boundary, and resumes delivery. The catch-up offers the text back; it is never retyped (AssemblyAI#10).
  3. The catch-up. When the user returns to the conversation, the attach client first prints a catch-up drawn from the journal, before the live conversation. It covers what changed since the user last left: what is waiting on the user (with Lavish links and the forwarding command), jobs that finished, failed or paused, holds with their causes, agents waiting in their own terminal, input the user still holds, and the saved unsent text. It is one line when nothing changed. Coordination narrates only if asked (AssemblyAI#10, AssemblyAI#14).
  4. A lost sign-in shows its native sign-in command in the catch-up as well as the status line (AssemblyAI#14, 07).

A second terminal

  1. The newest attach takes the conversation. The older terminal shows a one-line notice and only observes, and its unsent text is saved as if the user had left (AssemblyAI#10).

The Lavish server

  1. The daemon runs it. The daemon supervises the factory's own Lavish server, running AsmAI's pinned Lavish, so pending review pages survive agent restarts and a reboot. It checks the server periodically and restarts it if it is down (AssemblyAI#7, AssemblyAI#9, AssemblyAI#14).
  2. Local only. Lavish binds only to localhost. On a remote host it is reached through SSH port forwarding, and Coordination gives the page's URL and the forwarding command (AssemblyAI#7). asmai lavish lists the pending review links and the forwarding command, and --host forwards the remote Lavish port for the conversation and attach (AssemblyAI#9, 09).
  3. No agent runs Lavish. Agents never run Lavish themselves; the lavish skill is not shipped, because the daemon owns Lavish and renders decision requests (AssemblyAI#17).

Rendering decision requests

  1. Structured questions. A decision request whose answer surface is Lavish carries structured questions, each with an id, title, body, options and a recommendation (AssemblyAI#10). Grilling and Wayfinder questions arrive this way (AssemblyAI#10, 08).
  2. One standard layout. The daemon renders the questions in one standard layout, keyed to the decision version, and can tell when every question has an answer (AssemblyAI#10).
  3. The agent's own content. The requesting agent may put its own content above the questions, such as a prototype, a diff or a report (AssemblyAI#10).
  4. A new version, a new page. A new version of a request reissues its page, and answers from the old page are refused (AssemblyAI#10).

Collecting answers

  1. The daemon collects. The daemon, not an agent, collects what the user sends from a Lavish page: answers, comments and annotations, journaled word for word (AssemblyAI#10).
  2. Routing. The daemon routes what it collected to the owning leader's inbox, and Coordination confirms it in the conversation in one line (AssemblyAI#10).
  3. Partly answered pages. Open: question Q1 decides what happens when the user sends a page with some questions unanswered.
