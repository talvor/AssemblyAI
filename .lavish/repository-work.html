RESOLUTION

Recorded resolution

Confirmed by Phillip in Lavish on 2026-10-05 and recorded on GitHub: the resolution comment is posted on Define concurrent repository work and integration, which is closed; the map's Decisions so far gains its line; Choose validation and delivery ownership is narrowed as agreed; and two fog items are narrowed. ADR 0005 and the glossary terms (Repository instructions, Job branch, Assignment branch, Workspace) are kept with this board and your answers for archiving. This is a planning decision and authorizes no implementation.

  1. Scope: this ticket settles workspaces, branches, how work comes together on the job branch, keeping it current, and conflicts. Choose validation and delivery ownership keeps validation, review and tests, PR readiness and completion evidence, no-mistakes custody, when and by whom the job branch is pushed and its PR opened, and the line between a tested PR and a merge. Its question is narrowed to say so.
  2. AsmAI's own clone: each registered repository has an AsmAI-owned clone in the state directory, fetched from origin, and every workspace is made from it. Your own checkout is never used (ADR 0005).
  3. Workspaces: the daemon creates each workspace when it dispatches the assignment, starts the worker inside it, and is the only one that creates or removes them. A writing assignment works on its own assignment branch, made from the job branch's tip. A read-only assignment's workspace is fixed at the commit it examines, and its evidence names that commit. A job without a repository gives each assignment an empty scratch workspace. Staying inside is part of every worker's instructions, any write outside is an effect, and qualified provider write restrictions are switched on as a guard against mistakes. They are not a security boundary.
  4. Job branch: each repository job has one job branch, which becomes its PR. It starts from the default branch as fetched from origin, or from another origin branch you name, and the job records the commit it started from. Only one party writes a branch at any time.
  5. Accepted work: a worker takes in the job branch's tip before submitting. When the owning leader accepts with asmai accept, the daemon fast-forwards the job branch to the accepted commit as part of recording the acceptance. If the job branch moved after the result was submitted, the work goes back to the same worker to take in the new tip and submit again, which is not a rejection. Conflicts are always resolved by a worker inside an assignment.
  6. Keeping current: the job branch takes in the latest base before it is offered for review and before each later push. It merges the base in, unless the repository instructions ask for a rebase. Pushed history is rewritten only when the repository instructions require it, and then with force-with-lease. Resolving a conflict is ordinary writing work, and a choice between distinct viable approaches comes to you.
  7. Concurrent jobs in one repository: they run with no locks and no overlap report. A conflict is resolved in whichever job meets it when its branch is brought up to date. How many jobs run at once belongs to Define operating limits and visibility.
  8. Outside pushes: before every push the job fetches its branch from origin. Commits it did not make are kept and merged in, recorded as an outside change, and reported in one line. They are never force-pushed over.
  9. Assignment branches on origin: a worker commits and pushes its assignment branch whenever it submits a result, reports that it is blocked, or is cancelled, committing any uncommitted changes first. Each push is an effect. Pushing assignment branches and the job branch is part of every repository job's mandate, including research-only and planning-only jobs. Assignment branches stay on origin until you delete them, and none is ever opened as a PR.
  10. Notes: a note that its workflow already records in the issue tracker, such as a resolution comment or a PR review, is not copied. Any other note, such as research findings or a diagnosis log, is committed to the job branch, by a writing assignment. It goes where the repository already keeps such notes (its repository instructions or existing folders), otherwise under docs/<kind>/, and the result says where. A prototype stays on its own assignment branch on origin, and its verdict, with a pointer to that branch, is a note.
  11. Jobs that change no code: a repository job whose outcome is notes delivers like any other. Its job branch is pushed and opened as a PR holding its notes, for you to review and merge.
  12. Follow-ups: a follow-up to a job whose PR is still open continues on that job branch and PR, starting from origin's copy, so your fixups are included. A job branch belongs to one open job at a time. After the PR is merged or closed, a follow-up starts from the base with a new job branch and PR.
  13. Leaders' view: the daemon keeps one read-only view of each repository job at the job branch's tip, refreshed whenever the branch moves. Leaders read code and repository instructions there, the job's brief points to it, and leaders never write in it. It is not a workspace.
  14. Local cleanup: a writing assignment's workspace is removed once its work is on the job branch, and a read-only workspace when its assignment ends. A workspace whose assignment needs reconciliation is kept until the reconciliation is recorded. The workspace of cancelled or abandoned work is kept until the job ends; its work is already pushed. When the job ends, everything local to it is removed, and branches on origin stay. Scratch workspaces of a job without a repository are kept after it ends, until you remove them. Disk limits belong to Define operating limits and visibility.
  15. Repository instructions: agents follow the repository's instruction files, and both providers see AGENTS.md and CLAUDE.md, whichever exist. The repository's provider configuration (.claude settings, hooks, permission rules, MCP servers, .codex configuration) is not loaded. Repository instructions decide how work is done in that repository but never widen a mandate, and a conflict with the mandate is escalated. Your per-repository notes in AsmAI's configuration count as repository instructions. Whether a provider can load instruction files without project configuration is qualified per provider, and AsmAI can always pass their content itself. Skills a repository provides belong to Choose skill bundles and update policy.
  16. Commits: agents use your git identity and your existing git and gh credentials, and AsmAI handles no tokens. Every commit carries AsmAI-Job, AsmAI-Agent and AsmAI-Dispatch trailers, which a repository whose conventions forbid trailers can switch off.
  17. Shared resources: every workspace gets a slot number and its own temporary directory (ASMAI_SLOT and TMPDIR). A repository whose checks cannot run side by side says so, and agents run those checks through an asmai command that takes turns per repository.
  18. Records: the glossary gains Repository instructions, Job branch, Workspace, and Assignment branch. ADR 0005 records the AsmAI-owned clone and fast-forward on acceptance.
  19. Deferred to existing tickets: Choose validation and delivery ownership (as above, plus where review and validation evidence is recorded). Define operating limits and visibility (concurrent jobs per repository, workspace disk use, retained scratch workspaces). Choose skill bundles and update policy (skills a repository provides). Define v1 acceptance scenarios and evidence (loading instruction files without project configuration, provider write guards, concurrent jobs in one repository, outside pushes, a crash during a push). The configuration schema fog now also covers per-repository notes and declared one-at-a-time checks. The fog item on workflow variation is narrowed: repository conventions are carried by repository instructions.
