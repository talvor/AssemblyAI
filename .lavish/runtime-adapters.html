Providers and accounts

Both Claude and Codex are required at launch. AsmAI v1 is open-source and user-operated, including individuals running their own local or remote hosts. A hosted service, commercial distribution, and resale of provider access are outside this v1 direction; the specific open-source license remains to be chosen.

Subscription access only: each installer installs and signs into the unmodified provider CLIs themselves on the execution host. AsmAI must not initiate sign-in, collect or transfer provider tokens, or fall back to API billing. It may check readiness without exposing secrets and give actionable instructions. The provider CLI retains its own built-in authentication methods; AsmAI's supported operating mode is subscription-backed use.

Terminal conversation and human decisions

The primary conversation is the provider's interactive terminal, normally Coordination's. This supersedes browser-primary chat. Lavish remains required for reviews and all grilling/Wayfinder questions. A separate browser dashboard is not selected here.

Any agent can be inspected. Direct intervention outside Coordination is explicit: pause automated input, capture resulting answers or changes for the owner, and preserve the owner's control of worker scope and priority. Native permission prompts can be answered in the affected terminal with the decision recorded. Human input and automated input must not compete.

Staffing and fallback

Configure provider/model per role leader and a worker default per role, with explicit assignment overrides. Use the other configured, compatible subscription provider/model automatically only before first dispatch when the primary lacks access. Record and report the selection. If no suitable provider is available, pause affected work and continue independent authorized work.

After first dispatch, ask Phillip before changing provider, even if no output or side effect has been observed. For leaders, automatic selection is allowed before the leader first starts; replacing its provider afterward needs the same human decision. Resuming on the same provider after access returns is allowed. An approved replacement must reconcile existing effects and retain assignment context, grants, pending human decisions, and single ownership. Provider-native conversations are not assumed portable.

Integration direction and evidence still needed

Pursue a common approach based on the providers' unmodified interactive CLIs and attachable terminals, with provider-specific integration where necessary. The earlier unattended Codex-exec/Claude-print proposal and app-server/SDK pair are not selected. Choosing a terminal does not choose tmux, a supervisor, or a transport.

Support only explicitly tested runtime/adapter combinations, record versions, reject unsupported combinations with an actionable message, and qualify upgrades deliberately. Codex 0.157.0 and Claude Code 2.1.283 are observed candidate baselines only, not certified supported versions.

Proposed next evidence step: create “Validate interactive CLI coordination and intervention,” a focused prototype decision ticket to demonstrate both providers' own-login use, attachment, real human prompts and Lavish return, exclusive human/automated input, trustworthy waiting/completion signals, interruption/resume, and subscription-only readiness. It must establish a feasible adapter contract and tested candidate versions, or return a specific limitation for a new choice. No approval bypass, silent API fallback, or automatic replacement of the chosen integration. This prototype remains a future Wayfinder session.
