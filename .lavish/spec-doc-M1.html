Q1

How does M1 get its pinned Claude, its repository and its staffing?

Go to “What it adds” in the document

The milestone table leaves a gap. M1 runs a job on the fixture repository with a pinned Claude Code, and C3 (pinned copies reuse your sign-in) passes at M1's end. But `asmai providers install`, `asmai init`, `doctor` and the configuration file are listed in M2, and nothing lists `asmai repo add` at all. M1 needs a pinned Claude Code, the fixture repository registered, and a provider and model for Coordination, Engineering and Quality.

The draft's rule tables assume A.

Recommended: A. Each piece is real code that stays, as vertical slices should be, and M2 widens it rather than replacing it. B builds stand-ins that M2 must remove, and C3 would then pass on a path users never take.

Q2

Do leaders start on demand from M1?

Go to “What it adds” in the document

The milestone table puts leaders on demand in M5 (02 rules 51 to 53, C31). Before M5, the skeleton still needs Coordination's, Engineering's and Quality's leaders running. The sources do not say how they start until then.

The draft's rule tables assume A: 02 rule 51 in M1, rules 52 and 53 in M5.

Recommended: A. Starting a leader when work for its role arrives is the rule the factory keeps, and it is small; only stopping idle leaders and choosing their provider need M5's limits. B builds a start-up path M5 would replace.

Q3

How are demo paths recorded before M4?

Go to “Demo path” in the document

The end-of-milestone rule (AssemblyAI#27) keeps a terminal recording of each demo for you to watch. AsmAI's own per-dispatch recordings of agent terminals (03 rules 41 to 43) arrive in M4, so M1 to M3 cannot rely on them. They also record agents' terminals, not the terminal you would watch the demo in.

Recommended: A. One way to record every demo, from M1 on, shows you what the demo looked like. B adds M4's recording work to the walking skeleton, which is meant to be the thinnest path to a tested PR.

M1 Walking skeleton

M1 is the walking skeleton: on Claude only, one job travels from the user's request to a tested pull request on the fixture repository, end to end, through every layer it needs. Every later milestone widens it (AssemblyAI#27).

What it adds

  1. The daemon, on Claude only: asmai start and stop, the daemon, the store and its journal, daemon-owned terminals with hooks, nudges and asmai inbox, and attaching to the conversation (AssemblyAI#27).
  2. One job, end to end. Coordination opens a job from the user's witnessed message and hands it to Engineering. One writing assignment works in a workspace of AsmAI's clone, and its acceptance fast-forwards the job branch. Quality validates the head. The daemon pushes, the Engineering leader opens a draft pull request, and the daemon watches CI and marks the pull request ready. Coordination reports the link (AssemblyAI#27, 00).
  3. What the skeleton needs to run. Question Q1: how M1 gets its pinned Claude Code, the fixture repository's registration and its staffing before M2 adds asmai providers install, asmai init and the full configuration file.
  4. Leaders. Question Q2: whether leaders start on demand from M1, or all start with the factory until M5.
  5. The harness, in its own directory of talvor/asmai and built only into development builds, running M1's cases with the real pinned Claude Code under the harness's OS user (AssemblyAI#27, 11).

Builds on

M0 Groundwork: talvor/asmai, hosted CI with the fake provider, the fixture repository and the harness's OS users.

Demo path

A tested pull request on the fixture repository, end to end (AssemblyAI#27):

  1. The user opens the conversation with asmai and asks Coordination for a small change to the fixture repository.
  2. Coordination opens a job from that witnessed message, with its mandate and acceptance criteria, and hands it to Engineering.
  3. The Engineering leader assigns one writing assignment; the worker tests and commits on its assignment branch and submits; the leader accepts, and the daemon fast-forwards the job branch.
  4. Engineering hands validation to Quality; a Quality worker validates the exact head and reports no blocking finding.
  5. The Engineering leader asks for the push with asmai push, the daemon pushes, and the leader opens a draft pull request with the AsmAI section and records it as an effect.
  6. The daemon watches CI on the head, marks the pull request ready when it is green, and Coordination reports the link. The job ends.

Question Q3: how this demo is recorded, since AsmAI's own terminal recordings arrive in M4.

Exit checks

M1 ends when (AssemblyAI#27):

  • its tickets are closed;
  • the development tests are green on Linux and on macOS;
  • its qualification cases pass in the harness on Linux and have run on the Mac; a macOS failure becomes a ticket in M2 and does not hold up M1;
  • its demo path has run once on the fixture repository, with the terminal recording kept for Phillip to watch.

Not in M1

Codex, skills, asmai init and doctor (M2); decision requests, Lavish, Planning and Research (M3); the status line, catch-up and intervention (M4); caps, limits, holds and concurrent jobs (M5); fencing, full reconciliation and the service (M6); remote hosts (M7); releases and upgrades (M8).
